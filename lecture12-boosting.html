Boosting

We begin by initiating the algorithm discussed in the lecture from scratch and applying it to a dummy data set.

Show/Hide Code 
library(rpart)
set.seed(5076)
n <- 100
x1 <- round(runif(n, 0, 10), 0)
x2 <- round(runif(n, 0, 10), 0)
y <- round(10 + 3*x1 + x2 + rnorm(n, 0, 10))
dat <- data.frame(cbind(y, x1, x2))

# Initiate algorithm "by hand"
gb.manual <- function(lambda, d, ntrees){
  train_mse <<- c()                     #To keep track of training error
  resids <<- c()                        #To keep track of residuals
  rhats <<- c()                         #To keep track of tree predictions
  
  yhat_b <- mean(y)                     #First initialisation of prediction -> step 1
  r_b <- y - yhat_b                     #First initialisation of residuals  -> step 1
  
  for(b in 1:ntrees){
    ctrl <- rpart.control(maxdepth = d, cp = 0.001)  
    t <- rpart(r_b ~ x1 + x2, 
               control = ctrl)          #Fit tree to residuals              -> step 2a
    rhat_b <- predict(t, newdata = dat) #Predicted values of tree b         -> step 2b
    yhat_b <- yhat_b + lambda*rhat_b    #Updated prediction                 -> step 2b
    r_b <- y - yhat_b                   #Updated residuals                  -> step 2c
    # r_b <- r_b - lambda*rhat_b        #Could also write it like this, same thing
    
    # Save all the training mses, residuals, and tree predictions
    train_mse <<- c(train_mse, mean((y - yhat_b)^2)) #Double arrow saves object outside function
    resids <<- cbind(resids, r_b)
    rhats <<- cbind(rhats, rhat_b)
  }
  return(mean(y) + lambda*apply(rhats, 1, sum)) #Output final predictions   -> step 3
  # Could also return y - resids[, ntrees]
  # Or just yhat_b
}

#Run algorithm
yhat_manual <- gb.manual(lambda = 0.01, d = 1, ntrees = 1000)

#Final model training error
(gbm_manual_train_mse <- mean((y - yhat_manual)^2)) # Or just train_mse[ntrees]
[1] 102.1009

Example – California housing

Since this is our final analysis of this dataset, we will apply some feature engineering, a process of adapting/transforming/combining the existing information into new features to improve model performance.

Instead of using the total number of bedrooms, bathrooms, and people per neighbourhood, let’s use the number of households to convert these into per-house rates. We will also apply a 80/20 train-test split, here showing how a caret function can be used to do so.

We see that according to impurity-based importance, Income appears dominant, implying that it is highly effective at reducing training RSS and is frequently used in early splits. Permutation-based importance, on the other hand, reflects the extent to which the model’s predictive performance depends uniquely on a variable. Since Income is strongly correlated with the spatial predictors Latitude and Longitude, permuting it does not degrade predictive accuracy as dramatically as its split-based contribution might suggest. This highlights that impurity importance measures how much a variable is used in constructing the model, whereas permutation importance measures how much the model relies on that variable for prediction.

It’s also worth noting that two of our engineered features – average occupancy and average rooms – were somewhat influential according to both measures.

Although variable importance plots tell us which features are most important for predicting the response, they do not tell us how the predictors influence the predictions. For this, we can make use of partial dependence plots.

Partial dependence plots

Visualisation of the relationship between the predictors and the predicted outcome is limited to low-dimensional views. Although these “slices” of information can seldom provide a comprehensive depiction of the approximation, it can still provide a useful indication of how certain features influenced the predictions on average, especially when their interaction with other variables is limited.

The gbm package again allows us to easily produce the partial dependence plots. Figure 5 shows 1-dimensional partial dependence plots for the previously fitted model on the (feature-engineered) California dataset for four of the (non-location) features.

So far we have only discussed the base version of stochastic gradient boosting, but there are several variants that use the same basic principle whilst making changes to some aspects of the algorithm. One particularly powerful, relatively recent development is Extreme Gradient Boosting (XGBoost).

XGBoost

Since Chen and Guestrin (2016) first proposed XGBoost, it has become a highly popular choice for solving a wide range of machine learning problems, especially structured/tabular data. Conceptually, it is a gradient boosting method built from regression trees, but with several important refinements that improve statistical regularisation and computational efficiency.

To illustrate its application, we will analyse the California data one final time using the xgboost package. In earlier versions, it was convenient to tune XGBoost via caret::train(method = "xgbTree"). However, at time of writing (2026-04-29), changes in the underlying R objects created by xgboost v3.2+ can cause caret fits/tuning to fail. Therefore, we have the following options:

  1. Use xgboost’s built-in CV grid search tuning function – xgb.cv() – which also applies early stopping. The only additional requirement is that the data be transformed into an xgb.DMatrix object. The drawback here is that hyperparameter tuning and results plotting would have to be done “manually”, as opposed to using caret’s convenient built-in functions.

  2. Use a different model training framework instead of caret, for example the now widely-used tidymodels framework, or the more powerful (but less convenient) mlr3 package. Although these are good options, we will not be introducing them at this stage.

  3. Install a previous version of xgboost. This is not generally the recommended approach for long-term usage, however, for our purposes there is little functional difference between the older version used below and the latest version. Therefore, we will take this option.

Example – Titanic

Slow learning methods like gradient boosting generally tend to work better on larger datasets. Having said that, nothing prevents us from applying boosting to the Titanic data for comparison, even though it is relatively limited in size.

The benefit of a smaller problem is of course that the training goes quicker and it generally requires fewer trees, such that one can test more hyperparameter combinations for the same time cost. Subsampling is also unlikely to yield much, if any benefit, hence we will just use the gbm method.

We will search across trees from 500 to 6000 in increments of 500; \(d = 1, \ldots, 5\); and \(\lambda \in (0.001, 0.005, 0.01)\).

### Boosting

We begin by initiating the algorithm discussed in the lecture from scratch and applying it to a dummy data set.

```{r}
library(rpart)
set.seed(5076)
n <- 100
x1 <- round(runif(n, 0, 10), 0)
x2 <- round(runif(n, 0, 10), 0)
y <- round(10 + 3*x1 + x2 + rnorm(n, 0, 10))
dat <- data.frame(cbind(y, x1, x2))

# Initiate algorithm "by hand"
gb.manual <- function(lambda, d, ntrees){
  train_mse <<- c()                     #To keep track of training error
  resids <<- c()                        #To keep track of residuals
  rhats <<- c()                         #To keep track of tree predictions
  
  yhat_b <- mean(y)                     #First initialisation of prediction -> step 1
  r_b <- y - yhat_b                     #First initialisation of residuals  -> step 1
  
  for(b in 1:ntrees){
    ctrl <- rpart.control(maxdepth = d, cp = 0.001)  
    t <- rpart(r_b ~ x1 + x2, 
               control = ctrl)          #Fit tree to residuals              -> step 2a
    rhat_b <- predict(t, newdata = dat) #Predicted values of tree b         -> step 2b
    yhat_b <- yhat_b + lambda*rhat_b    #Updated prediction                 -> step 2b
    r_b <- y - yhat_b                   #Updated residuals                  -> step 2c
    # r_b <- r_b - lambda*rhat_b        #Could also write it like this, same thing
    
    # Save all the training mses, residuals, and tree predictions
    train_mse <<- c(train_mse, mean((y - yhat_b)^2)) #Double arrow saves object outside function
    resids <<- cbind(resids, r_b)
    rhats <<- cbind(rhats, rhat_b)
  }
  return(mean(y) + lambda*apply(rhats, 1, sum)) #Output final predictions   -> step 3
  # Could also return y - resids[, ntrees]
  # Or just yhat_b
}

#Run algorithm
yhat_manual <- gb.manual(lambda = 0.01, d = 1, ntrees = 1000)

#Final model training error
(gbm_manual_train_mse <- mean((y - yhat_manual)^2)) # Or just train_mse[ntrees]
```

So far we have only discussed the base version of stochastic gradient boosting, but there are several variants that use the same basic principle whilst making changes to some aspects of the algorithm. One particularly powerful, relatively recent development is Extreme Gradient Boosting (XGBoost).

### XGBoost

Since @xgboost first proposed XGBoost, it has become a highly popular choice for solving a wide range of machine learning problems, especially structured/tabular data. Conceptually, it is a gradient boosting method built from regression trees, but with several important refinements that improve statistical regularisation and computational efficiency.

To illustrate its application, we will analyse the California data one final time using the `xgboost` package. In earlier versions, it was convenient to tune XGBoost via `caret::train(method = "xgbTree")`. However, at time of writing (`r Sys.Date()`), changes in the underlying R objects created by `xgboost` v3.2+ can cause `caret` fits/tuning to fail. Therefore, we have the following options:

1. Use `xgboost`'s built-in CV grid search tuning function -- `xgb.cv()` -- which also applies **early stopping**. The only additional requirement is that the data be transformed into an `xgb.DMatrix` object. The drawback here is that hyperparameter tuning and results plotting would have to be done "manually", as opposed to using `caret`'s convenient built-in functions.

2. Use a different model training framework instead of `caret`, for example the now widely-used [tidymodels](https://workflowsets.tidymodels.org/articles/tuning-and-comparing-models.html) framework, or the more powerful (but less convenient) [mlr3](https://mlr3.mlr-org.com/) package. Although these are good options, we will not be introducing them at this stage. 

3. Install a previous version of `xgboost`. This is not generally the recommended approach for long-term usage, however, for our purposes there is little functional difference between the older version used below and the latest version. Therefore, **we will take this option**.

```{r warning=F, message=F}

library(xgboost)
```

The only hyperparameters we will search over are: 

- Number of trees $B$ from 5000 to 35000 in increments of 5000 
- Tree depth $d \in (3, 6, 9)$ 
- Learning rate $\lambda \in (0.005, 0.01, 0.05)$ 
- Feature subsampling per tree (similar to $m$ in the random forest, only at tree level) $\in \{0.5,  1\}$ 
- Row subsampling will be set to 0.7 

Below we see all the hyperparameters that must be specified when creating a search grid for XGBoost. Note that separate models are not run for different numbers of trees; the chain is simply extended, allowing us to use even more granular numbers of trees than this should we want to. 

Despite the relatively limited search, this will still take several hours to run, even on high performance hardware.

The best model used tree depth equal to the highest tested value (faster learning), coupled with the lowest learning rate (slower learning). ### Example -- Titanic

Slow learning methods like gradient boosting generally tend to work better on larger datasets. Having said that, nothing prevents us from applying boosting to the Titanic data for comparison, even though it is relatively limited in size. 

The benefit of a smaller problem is of course that the training goes quicker and it generally requires fewer trees, such that one can test more hyperparameter combinations for the same time cost. Subsampling is also unlikely to yield much, if any benefit, hence we will just use the gbm method.

We will search across trees from 500 to 6000 in increments of 500; $d = 1, \ldots, 5$; and $\lambda \in (0.001, 0.005, 0.01)$.

```{r}
                   bag.fraction = 1,

                   n.cores = 10,
```

```{r}

tgbm_pred_wrapper <- function(object, newdata) {
  p <- predict(object, newdata = newdata, n.trees = d, type = 'response')  # d = chosen number of trees above
  factor(as.integer(p >= 0.5), levels = levels(y_train))
```
